# 研究与参考记录

> 研究截点：2026-10-10（UTC）。本项目的主轴是交互与视觉；下列研究用于界定六个品牌、避免失实叙述和说明实现方法，不把流量数据当成全球市场份额，也不把公司指控写成已裁定事实。

## 1. Three.js 与视觉参考：读到什么、如何转化

### Three.js 官方资料

实现前阅读并核对了 Three.js 手册的 Installation、Picking、Responsive Design、Scene Graph、Matrix Transformations、Cleanup、WebGL Compatibility Check，以及 `Raycaster`、`Object3D` 源码/API。项目选择 `three@0.186.1`，使用 npm 构建时打包成传统 `<script>`，而不是运行时模块导入或 CDN；原因是项目必须能离线、用相对路径，并可直接通过 `file://` 打开。

| 参考方法 | 在项目中的用途 | 有意不做的事 |
| --- | --- | --- |
| Installation：npm 包与生产构建 | Three.js 是构建期依赖；把引擎和应用打进本地经典脚本，静态发布不需要服务器端程序 | 不使用手册的 CDN import map、远程模型或运行时网络请求 |
| Responsive Design：以 CSS 尺寸更新相机，以有限像素比控制 drawing buffer | resize 时同步画布缓冲区与相机比例；对设备像素比和总像素数设上限，避免手机过载 | 不把设备的最高原生分辨率无条件拿来渲染 |
| Picking：`Raycaster.setFromCamera()`、归一化设备坐标、近到远的命中序 | 仅在按下/拖动开始时对 27 个 cubie 上的 54 个贴片拾取平面做射线检测，读取命中 cubie、贴片 ID 与面法线，识别“拖层” | 不每帧遍历场景做拾取；不把透明图层当作可见 UI，也不为这个低复杂度方块引入 GPU picking |
| Scene Graph：父子局部坐标 | cubie 归魔方根节点管理；临时层组只负责一次转动；六个小世界是 `scene` 的兄弟节点，居民一直处于场景坐标并沿固定外环旅行 | 不把小世界或居民挂在魔方根节点下，避免它们随层扭动 |
| Matrix Transformations：position/quaternion/scale、world matrix 更新、`Object3D.attach()` | 临时层组重挂 cubie 时保持世界变换；层结束后按离散的整数格位和 90° 旋转矩阵校正，防止浮点误差累积 | 不使用非均匀缩放父节点，不靠逐帧累计近似角度作为最终状态 |
| Cleanup：显式管理几何、材质、纹理 | 几何与 54 张程序化纹理全程复用；动画不持续创建新资源，也不重建整场景 | 不在自动循环中反复加载贴图或累积 WebGL 资源 |
| WebGL Compatibility Check | 初始化 WebGL2 渲染器并捕获失败；不可用时显示简短、非游戏内的兼容性说明 | 不在不支持的设备上静默呈现空画布 |

Raycaster 命中法线需要结合 cubie 的世界变换还原到魔方局部坐标；反向面拾取也受材质正反面设置影响。应用只对朝外的可见方块表面拾取，坐标由 canvas 的 `getBoundingClientRect()` 归一化，因此画布不是全窗口时也能正确映射。视角操作和层扭转分别使用“从空白开始的拖动”和“从 cubie 表面开始的拖动”；手机双指与滚轮负责缩放。

### The Book of Shaders

已完整阅读第 02、03、05、06、07、09、11、12、13 章。它们有助于理解坐标、形状、过渡、重复结构与受控变化。项目仅采用以下一般性设计思路：

- 让动画由归一化位置、时间和局部状态驱动；
- 通过连续曲线、距离和邻接关系构造明确边界与平滑变化；
- 用局部坐标与规律网格表达结构；
- 让少数有含义的参数缓慢演化，而不是随机抖动；
- 将图案、连接和起伏限制在可解释的范围内。

这不是 GLSL 教程的复刻：本项目用 Three.js 网格、Canvas 2D 程序化贴图、对象变换和 JavaScript 状态更新表达这些一般概念，不复制书中的代码、文字、图片、作品或截图。**该仓库的 LICENSE 明确限制内容再分发与项目复用**，所以本项目只引用其网址，不把参考文件放进交付物。

## 2. 六个系列的选择与资料边界

### 选择口径

选定 **OpenAI/GPT、Anthropic/Claude、Google/Gemini、DeepSeek、Alibaba/Qwen、Z.ai/GLM**。这不是对“全世界最受欢迎六个模型”的断言，而是在六个槽位限制下，兼顾公开产品系列、开发者路由流量、近期开源/接口生态和跨地区辨识度的设计选择。

OpenRouter 的模型路由排名页面在 2026-10-09 显示一周请求流量份额：DeepSeek 21.8%、Google 21.5%、OpenAI 18.2%、Z.ai 6.6%、Qwen 6.2%、Anthropic 2.5%；按该页面同一口径合计 76.8%。**这是 OpenRouter 的请求流量，不是全球用户数、收入、模型质量排名，也不代表所有使用渠道。** [OpenRouter Rankings](https://openrouter.ai/rankings)

另一类数据也不能直接拼接：Sensor Tower 的《State of AI 2026》按消费者 AI assistant app 的使用/时长等维度统计，报告称 2026 年第一季度 ChatGPT、Gemini 与 DeepSeek 占其统计的 AI assistant app 使用时长近九成。它和 OpenRouter 的 API/路由请求不是一个分母。[Sensor Tower: State of AI 2026](https://sensortower.com/blog/state-of-ai-2026)

Meta AI/Muse、xAI/Grok 以及其他品牌也是值得考虑的候选。Meta 的跨 Facebook、Instagram、WhatsApp 等产品触达数据不能等同于独立模型 API 使用量；Grok 也有 X 与独立产品等不同入口。受限于六面，本次把 OpenRouter 明确可观察到的系列与消费产品知名度结合起来；这是一项项目取舍，不是排除其他品牌的事实判断。

## 3. 梗与彩蛋：只用有边界的历史梗

项目只安排一个极小的草莓造型彩蛋，藏在 OpenAI/GPT 对应的小世界结构下方；不显示“数错字母”的文字，不作为模型能力提示，也不声称当前模型仍普遍犯同一错误。

核对到的背景：2024 年 8 月 TechCrunch 与 Inc 分别记录了 ChatGPT 在“strawberry 有几个 r”对话中的错误回答与当时的社交传播；之后有关于字符级任务的学术研究继续考察这类失败。草莓一词实际有三个 r。该现象是特定版本、提示和时点下的真实轶事，**不能外推为所有模型、所有版本或现在的模型表现**；学术界对具体成因也有不同分析，故游戏不把“tokenization 是唯一原因”写成定论。

- [TechCrunch，2024-08-27](https://techcrunch.com/2024/08/27/why-ai-cant-spell-strawberry/)
- [Inc，2024-08-28](https://www.inc.com/kit-eaton/how-many-rs-in-strawberry-this-ai-cant-tell-you.html)
- [Cosma et al., *The Strawberry Problem*, arXiv / EMNLP 2025](https://arxiv.org/abs/2505.14172)
- [Fu et al., *Why Do LLMs Struggle to Count Letters?*, arXiv 2024](https://arxiv.org/abs/2412.18626)

争议指控、历史生成失误和品牌争端不做成视觉梗，也不拿来推动游戏性能差异。

## 5. 研究转为实现时的规则

1. 运行不向任何公司 API 发送输入，不收集行为数据，也不联网取材。
2. 以确定性的离散状态处理魔方；每个贴片只对应一个能力单元，世界景观从当前九格与固定权重推导。
3. 动画相位、住民迁移和自动循环均受界限约束，不使用逐帧随机游走。
4. 六个小世界是魔方的场景兄弟节点；转层改变数据，不改变它们的世界坐标。
5. 不用强发光、全屏后处理、外部图片/字体、粒子喷发或额外游戏 UI。
6. 如果某个机制、品牌资料或浏览器行为没有完成实测，在验证记录中明确标记，不以设计意图冒充通过测试。
